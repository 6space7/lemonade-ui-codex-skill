# No-Dashboard Product Proof

Use this for landing pages and hero sections when the model keeps creating dashboard-like app previews.

The goal is not to hide the product. The goal is to stop using a full fake software screen as the automatic proof object.

No-dashboard proof must still pass `composition-discipline.md`. Do not replace dashboard slop with poster-collage slop.

## Default Rule

For vague SaaS, CRM, AI, devtool, finance, and product landing prompts, default to:

```text
Dashboard/app screen: no
```

Use a dashboard, admin panel, table/detail workspace, or framed app screen only when:

- The user explicitly asks for a dashboard, admin panel, analytics view, internal tool, or app screen.
- The product is genuinely dashboard-first and the main user job is browsing or operating that surface.
- Real screenshots exist and the user wants them used.
- The hero concept requires a workbench and the screenshot review proves it is not wallpaper beside marketing copy.

If none of those are true, choose a non-dashboard proof object.

## Non-Dashboard Proof Objects

Prefer one of these:

- **Selected object card:** one record, file, deal, ticket, order, clip, deployment, invoice, or customer.
- **Output artifact:** generated email, report, video clip, diff, export, receipt, summary, invoice, or calendar event.
- **Before/after strip:** messy input -> product action -> clean output.
- **Transcript/message:** call note, chat, email, comment, voice snippet, or meeting line becoming an action.
- **Action capsule:** one command, approval, publish, deploy, assign, send, reconcile, or export control.
- **Object stack:** layered cards/files/records that feel physical, cropped, and inspectable.
- **Timeline fragment:** three events that explain the change without showing a whole app.
- **Media/object stage:** real media, product object, device, document, canvas, or rendered result.
- **Interactive control surface:** one slider, scrubber, configurator, command palette, upload/drop target, or editor fragment.

These can contain UI, but they should not read as a complete dashboard window.

They should also remain legible, plausible, and restrained. A selected object card is not a license for random tilt, giant labels, fake scores, or neon decoration.

## CRM Without Dashboard

For a vague CRM hero, avoid a full queue/detail dashboard by default.

Use:

- One stale deal card with risk, owner, value, and next action.
- A call transcript line transforming into an email draft.
- A renewal note, approval button, and scheduled follow-up receipt.
- A pipeline card stack with one highlighted deal.
- A handoff note attached to a contact card.
- A before/after: scattered call notes -> approved follow-up.
- A calendar task slip tied to one account.

If you need a list, show two or three physical cards or a cropped strip, not a full app screen with columns and nav.

## Visual Moves

- Make the artifact oversized, cropped, floating, printed, stacked, pinned, glowing, or staged.
- Keep the main artifact mostly straight and readable; use rotation sparingly.
- Let the artifact break the frame or sit inside a shaped poster field.
- Put headline and CTA around the artifact instead of placing a dashboard beside copy.
- Use microcopy on the object itself instead of a paragraph explaining the product.
- Show one action changing state, not a static software wallpaper.

## Reject

- Browser chrome or desktop app chrome used as the hero proof.
- Noisy poster collage used as proof: huge broken headline, tilted card, loud backing shape, fake metric badge, and floating note all at once.
- Multi-pane queue/list/detail/action layouts when the user did not ask for an app screen.
- A dashboard-like rectangle beside a headline, paragraph, and CTAs.
- Fake navigation inside the proof object.
- Four columns of software UI pretending to be a landing-page visual idea.
- Metrics rows that repeat data already shown in the artifact.

## Review Questions

- If the software rectangle were removed, would the page still have a visual idea?
- Does the artifact look like one memorable object, or a fake product screenshot?
- Did the user actually ask for a dashboard/admin/app view?
- Could the proof become a card, transcript, output, receipt, timeline, or before/after instead?
- On mobile, does the first viewport show one useful artifact instead of a tiny full screen?
